# Анализ качества и архитектурные решения

## Область анализа

Первичный анализ был основан на чтении исходного кода без запуска по исходному
ограничению задачи. После отдельного разрешения пользователя добавлены и выполнены
50 тестов, Ruff и mypy; результаты описаны в [testing.md](testing.md).
Ниже сохранены архитектурные выводы. Они не являются доказательством полной
корректности или измерением производительности.

## Что было проблемой

1. `api/routes.py` совмещал HTTP, SQL, обработку транзакций, импорт и экспорт.
   Изменение хранения или бизнес-правила требовало менять транспортный слой.
2. `logic.py` и `services/requirement_service.py` содержали две реализации одних
   операций; маршруты использовали только одну. Правки легко расходились.
3. Репозитории и функции выполняли собственные `commit`. Создание требования
   сохранялось до истории, импорт фиксировался по одному требованию. Поздний
   `rollback` не мог отменить уже сохранённые части операции.
4. Список требований вызывал загрузку входящих/исходящих связей для каждой строки.
   Число SQL-запросов росло с числом требований; это структурный вывод из кода,
   а не результат измерения производительности.
5. Удаление проекта массово удаляло требования без явной очистки истории.
   Удаление требования затем пыталось создать историю с FK на удалённую строку.
6. При создании требования не проверялось существование проекта. Без контроля
   внешних ключей SQLite это позволяло записать некорректную ссылку.
7. API принимал произвольные словари, преобразовывал Enum внутри обработчиков,
   ловил широкие исключения и возвращал клиенту `str(exc)`, включая ошибки ORM.
8. ORM-модели формировали HTTP-словари; бизнес-логика зависела от SQLAlchemy Session.
9. Импорт модулей создавал глобальный engine. Зависимости проекта не имели
   единого описания пакета; UI-ресурсы жили отдельно от устанавливаемого кода.
10. DOCX-документация описывала `<конец>`, а парсер распознавал только `<end>`.

## SOLID: оценка и изменения

### S — Single Responsibility

Наиболее заметное нарушение было в маршрутах и `logic.py`: транспорт, хранение,
бизнес-правила и файлы имели общие причины изменения. Теперь маршруты адаптируют HTTP,
сервисы реализуют сценарии, репозитории исполняют SQL, файловые адаптеры работают
с форматами документов. Фабрика приложения отвечает за сборку зависимостей.
Дублирующий старый код удалён, вместо сохранения двух параллельных архитектур.

### O — Open/Closed

Раньше импортёр, экспортёр и ORM создавались или вызывались напрямую в бизнес-коде.
Теперь сервисы принимают протоколы `RequirementParser`, `ReportExporter`, `UnitOfWork`.
Адаптеры документов можно заменить аргументами `create_app`, хранение — через границу
`get_uow`. Новый бизнес-сценарий всё равно может требовать изменения сервиса:
OCP не означает запрет на изменение любого существующего кода.

### L — Liskov Substitution

В старом проекте не было выраженной иерархии доменного наследования; утверждать,
что LSP был нарушен, оснований недостаточно. Новая архитектура использует композицию
и структурные протоколы. Их поведенческий контракт: чтение не фиксирует транзакцию,
`get` возвращает `None` при отсутствии, операции репозитория не выполняют `commit`,
все репозитории Unit of Work участвуют в одной транзакции, наружу выходят снимки
сущностей. Один только `Protocol` не доказывает соблюдение этого контракта заменой.

### I — Interface Segregation

Вместо универсального репозитория с произвольными CRUD-операциями введены отдельные
интерфейсы проектов, требований, связей и истории. Парсер и экспортёр имеют отдельные
контракты. Unit of Work объединяет репозитории ради общей транзакции; этот небольшой
фасад оставлен осознанно, без отдельной абстракции для каждой строки SQL.

### D — Dependency Inversion

Домен использует только стандартную библиотеку. Прикладные сервисы зависят от
своих протоколов и независимых сущностей; они не знают SQLAlchemy, FastAPI, openpyxl
и python-docx. SQLAlchemy-адаптеры преобразуют ORM-строки в dataclass-снимки.
Транспорт получает сервисы через dependency injection. Pydantic в прикладных командах
— осознанная зависимость для единой валидации HTTP и файлового импорта; абсолютная
независимость от любой сторонней библиотеки не являлась целью.

## Транзакционная граница

Один Unit of Work создаётся на запрос. Репозитории могут выполнять `flush` для
получения ID и значений по умолчанию, но фиксирует данные только прикладной сервис.
История создания/изменения добавляется до общего `commit`. Импорт сначала разбирает
и валидирует документ, затем записывает все требования и историю общей транзакцией.
При любом незавершённом запросе сессия откатывается и закрывается.

SQLAlchemy engine создаётся в lifespan фабрики и освобождается при остановке.
Конфликт ограничений хранения переводится в прикладную ошибку `Conflict`, далее —
в HTTP `409`. Неожиданные исключения журналируются и возвращают общее сообщение `500`.

Удаление требования и проекта очищает связанные строки в порядке внешних ключей.
Постоянный аудит удалений с текущим FK не реализован: это потребовало бы изменения
схемы. Поле `deleted_by` используется в серверном логе. Существующие осиротевшие
строки, если они есть, не исправляются автоматически.

## Совместимость и структурирование

Сохранены URL, имена полей успешных ответов, значения Enum, имена/типы столбцов
и исходный SQLite-путь при запуске из репозитория. При запуске сервера не выполняются `create_all`,
`ALTER TABLE`, перенос данных и автоматические миграции. SQLite теперь включает
проверку FK на новых соединениях, поэтому ранее допускавшиеся некорректные операции
будут отклонены. Ужесточение валидации и коды ошибок описаны в README.

Код перенесён в `src/tracereq`; пакет устанавливается через `pyproject.toml`.
HTML/CSS/JS включены как package data. Метаданные и зависимости не дублируются
в requirements.txt. Совместимые точки запуска сохранены.

Для списка требований используются отдельная загрузка требований и единая загрузка
связей проекта; группировка выполняется в памяти. Снимки не содержат lazy relationships.
XLSX-адаптер получает готовый отчёт, не обращается к ORM и не оставляет временных файлов.

## Оставшиеся ограничения

- Автоматические проверки и HTTP smoke-тест проходят; выполнение JavaScript в браузере,
  другие СУБД и нагрузочные характеристики отдельно не проверялись.
- Списки не имеют пагинации; матрица и XLSX целиком формируются в памяти.
  Для крупных проектов потребуется отдельное решение по объёмам данных.
- DOCX проверяется по расширению и разбору содержимого; лимит чтения не заменяет
  ограничения multipart/распаковки и HTTP-запроса при эксплуатации.
- Аутентификация, права доступа и оптимистическая блокировка конкурентных изменений
  отсутствовали и не добавлены в рамках архитектурной переработки.
- JavaScript перенесён в пакет с сохранением поведения, но большой `main.js` не разбит
  на модули: этот рефакторинг относится к Python-архитектуре.
- Диапазоны зависимостей заданы, но lock-файл не генерировался. Для воспроизводимого
  развёртывания нужен lock, полученный выбранным менеджером в целевом окружении.
- Не добавлены новые ограничения уникальности связей, схемы аудита или индексы:
  это отдельные изменения базы данных, исключённые условиями задачи.

## Основания для технических решений

- [SQLAlchemy: управление Session и транзакциями](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).
- [Pydantic: модели и валидация](https://docs.pydantic.dev/latest/concepts/models/).
- [Python Packaging: src layout](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/).

Для первого запуска без БД добавлена отдельная команда `init-db`: она создаёт только новый SQLite-файл и отказывается изменять существующий.
